# AGENTS.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

AI Designer: an Electron desktop application where users generate multi-file designs (HTML / Vue3 / React) through natural-language conversations, with live previews, version management, and export. The UI component library is antdv-next (not ant-design-vue). All code comments must be in English and explain "why" rather than "what was done"; keep the same comment style and density in new code.

## Common commands

```bash
pnpm dev                # Start development (electron-vite)
pnpm typecheck          # = typecheck:node (main-process tsc) + typecheck:web (vue-tsc)
pnpm lint               # eslint --cache (Prettier runs through an ESLint plugin)
pnpm vitest run                          # All tests
pnpm vitest run src/main/skills/scan.test.ts   # A single test file
pnpm db:generate        # Generate SQL migrations after schema.ts changes (drizzle-kit)
pnpm build:mac / build:win
```

All three checks must pass before delivery: `pnpm typecheck && pnpm lint && pnpm vitest run`.

## Architecture overview

Three-process architecture, with the contract centralized in one place:

- `src/shared/types.ts` — **The sole contract between the main and renderer processes**. The `DesignerApi` interface defines the entire `window.api` surface. Only types belong here; do not import from `src/main` (that pulls the main process into the web project, causing TS6307).
- `src/main` — Main process: DB, AI orchestration, skill scanning, MCP, preview protocol, IPC.
- `src/preload/index.ts` — A handwritten `api` object literal, with one `ipcRenderer.invoke` line per method. Its `DesignerApi` type annotation makes missing implementations compile-time errors.
- `src/renderer` — Vue3 + pinia + antdv-next, with pages in `pages/*/index.vue` + `pages/*/components/`. `ref`, `computed`, etc. are auto-imported by unplugin; do not write imports for them.

### Adding an IPC method (four required steps)

1. Write pure functions in `src/main/<domain>/` (treat all renderer arguments as untrusted input; file paths must be protected against escaping allowed boundaries; see `skills/files.ts`).
2. Register a `domain:action` channel in `registerIpc()` in `src/main/ipc/index.ts`.
3. Add the signature to `DesignerApi` in `shared/types.ts`.
4. Add a line to the `api` object literal in `src/preload/index.ts`.

Pitfall: IPC uses structured clone, so Vue reactive proxies cannot be passed through it (convert them to plain data first; see `toPlainAnswer` in `stores/chat.ts`). Pass Buffer data as ArrayBuffer.

### Sources of truth (identify the relevant one before changing a feature)

| Data | Source of truth | Notes |
| --- | --- | --- |
| Projects / conversations / messages / versions | SQLite (drizzle, `src/main/db/`) | schema.ts is the sole source of truth; migrations are compiled into the bundle; **never change published migrations** |
| Overall project visual direction | The project's `styleBrief`, optional `designDocument`, and `visualStylePriority` fields | A single persisted visual-guidance configuration; combine compatible rules and resolve conflicts using the selected priority. Generate `theme.css` from this guidance. On the first turn of an empty project, after the user skips confirmation, an independent-dimension fallback may be used to complete the turn, but must not be persisted as a preference |
| Skills | Filesystem directories | Scan order determines override priority: `~/.antd-designer/skills` > `~/.agents/skills` > `~/.claude/skills` > built-in `resources/skills` (see `skills/scan.ts`). **There are no database-backed skills**; the directory name is the identity |
| MCP | `~/.antd-designer/mcp.json` | Secrets do not go in this file; they go through `secrets.json` (encrypted with safeStorage); configuration contains only `${VAR}` placeholders |
| Marketplace listings | The remote `marketUrl` configured in settings | Empty when unconfigured; fetch failures do not throw; status is reported through `market:status` |
| Application configuration | `~/.antd-designer/config.json` | Small, flat key-value settings; growing structured data belongs in SQLite |

Historical lesson: skills/MCP once existed in both the DB and files, with neither side able to see the other. This was ultimately consolidated by removing the tables entirely. **Do not introduce a second source of truth again**.

### AI conversation pipeline (src/main/ai/)

References to StyleBrief below also include optional DESIGN.md under the selected source priority.
Both empty is the only absence of recorded visual guidance. The document is immutable to model tools;
`set_style_brief` updates only the text, and rollback must never modify the document or its priority.

`chat-service.ts` is the streaming orchestration core. Design conversations and plain chat share the same pipeline, branching according to whether `project` exists:

- Two protocols: models with tool capabilities use the **tool protocol** (file reads/writes through tools, response body entirely explanatory); long-tail models use the **markers protocol** (full-file rewrites with `<antdFile>`). Both persist through `SessionVfs`. The tools VFS write gate mechanically locks only initial projects where "StyleBrief and DESIGN.md are empty and no files exist yet"; for other overall style updates, the prompt protocol requires a successful `set_style_brief` call before writing files. In markers mode, the first turn of an empty project may only present 2–3 directions in the response body and wait; file output is forbidden. On the next turn, output `<antdStyleBrief>` first only if the user supplies a direction, or `<antdUseStyleFallback />` first only if the user explicitly skips. After streaming ends, persist StyleBrief first, then load the staged files into the VFS and create the artifact. If persistence or the markers commit fails, leave neither a new theme nor this turn's files behind; the visual markers themselves do not enter the VFS, artifact, or response body.
- Tool calls are capped **by call count** (count calls, not steps; one step may run multiple calls in parallel). The user configures the hard limit: project `settings.toolCallLimit` > global `AppConfig.toolCallLimit` (default 80), **0 = unlimited** (only the cumulative-input circuit breaker at 5× the context window remains). The soft threshold (history compression) and reread-blocking threshold are derived at 50% / 75% of the hard limit; unlimited mode falls back to fixed values of 20 / 30. See `resolveToolLimits` in `context-governor.ts`.
- Skills are **manually selected, with zero loaded by default**: in plain chat, only selected skills are available (unselected skills do not even appear in the L1 catalog); in design conversations, built-in skills (craft-* / target-* / design-seed, including user overrides with the same names) take effect automatically. Selected = listed in the catalog and available for activation (progressive disclosure); **there is no full-text injection path**.
- MCP connects per turn (only when selected; connections must close when streaming ends, leaving no orphan child processes), using direct `@modelcontextprotocol/sdk` connections wrapped with `dynamicTool` (AI SDK v7 has no built-in MCP client).
- The system prompt (`prompts/index.ts`) is **partitioned by stability**: stable project sections come first for prefix caching (identity / charter / target contract / tech stack / craftsmanship baseline / skill catalog), followed by sections that vary per turn (current file tree / preview errors / lint results / final self-check pinned last for recency). **Do not insert per-turn content into the stable section**. Target templates (routed by the active target) and local authorization scope (including paths identified this turn) look like project properties but may change each turn, so they occupy the **last slot** in the stable section: prefix caching stops at the first differing byte; placing them in the middle also invalidates everything after them.
- **Anthropic caching uses breakpoints** (`prompt-cache.ts`): without `cache_control` in the request, nothing is cached. Breakpoints are marked on messages (the provider places them on the message's last block, meaning "cache through here", including tools and system). A breakpoint **looks back only 20 blocks**, while one tool-call step produces two blocks, tool-call + tool-result. Marking only the last message means that after dozens of calls, the next step cannot reach the previous step's entry. Therefore, add a breakpoint every 15 blocks working backward from the end, up to 4 (Anthropic's limit; excess breakpoints are silently ignored). The OpenAI protocol caches automatically on the server and does not recognize this field; the function returns its input unchanged for it. Runtime reminders injected into messages **must not contain counters that change every step** (that would change the prefix every step).
- The quality feedback loop has two levels: within a turn and across turns. **Within a turn**: after a write tool succeeds, `compile-probe.ts` performs a real compilation and attaches errors to the tool result; multimodal models also have `capture_preview` (`capture-tools.ts` + offscreen screenshots in `preview/capture.ts` + direct serving of the session VFS through `preview/session-registry.ts`), allowing the model to review the rendered result. **Across turns**: `slop-lint.ts` checks for an AI-generated look (aesthetic rules are exempted when explicitly named in the original StyleBrief), finalization provides a compilation fallback, and preview runtime errors are collected. All are bound to artifactId and fed back into the prompt on the next turn; successful preview mounting (iframe ready) clears old errors for that version.
- **Visual direction mechanism**: the project's `styleBrief`, optional `designDocument` and `visualStylePriority` together are the sole source of truth for overall visuals. DESIGN.md never changes skill activation or workflows, technical contracts, safety or accessibility. Resolve conflicts in this order: "the user's explicit global style for this turn > project visual guidance (selected source first, compatible rules combined) > continuity of the current artifact > skill quality guardrails". Local component or single-page exceptions must not update StyleBrief. If both visual sources are empty and no files exist, ask first; only after the user skips may a fallback be generated along six independent dimensions: color / lightness-darkness / density / geometry / surfaces / navigation. Do not persist the fallback. If the brief is empty but files exist, continue the current visuals.
- `design-seed` provides only a generation method, semantic token contract, and accessibility and consistency guardrails, not a concrete theme to copy. Generate each project's `theme.css` from StyleBrief; if a design exists without a brief, continue the current artifact; use a non-persisted independent-dimension fallback only after the user skips on the first turn of an empty project. `antdv-theme` maps the same project direction to component tokens; it is not a library of preset recipes.
- Design system design and evolution documentation: `docs/prompt-skills-v2.md` (target templates / craft / question mechanism and writing rules: make rules binary, countable, and expressed in observable terms; each rule has only one home).

### Multi-agent collaboration groups (src/main/ai/group-service.ts)

Chatroom + @ handoffs: when creating a group, save the complete configurable member definitions as `settings.members: GroupMember[]`; the five built-in roles serve only as group creation templates. Members use ULIDs as stable identities, each carrying a persona, model row, and file-based skills. The user starts by @-mentioning members; agents produce Markdown documents (the message is the document, with no VFS / versions / code), and each hop uses that member's own model and skills. Parsing of structured mentions and exact natural `@member-name` mentions is centralized in `shared/group-mentions.ts`. Reuse conversations (kind='group') and messages (author stores the member ULID); events use a separate `group:stream` channel; group chat history is assembled into a **single** transcript (some providers reject consecutive user messages). Agents use local-file, time, and selected-skill activation tools; local files are authorized through workspace roots scoped by conversationId. Groups are editable (`group:update`; creation and editing share the dual-mode `GroupFormModal`): existing members **may only have their configuration changed, not be deleted** (historical message authors reference member ULIDs; deleting a member would orphan their messages; removal is reserved for future soft deletion), and new members may be added. Reject saving while handoffs are running (member configuration is reread at each hop's start, so changing it mid-chain would change the persona midway).

**Handoffs form a tree, not a chain**: mentioning several members in one message fans out into that many branches, **starting simultaneously** (`mentionAssignments` preserves order of appearance and deduplicates by member; each member receives only the instructions between their own @ mention and the next @ mention). After each hop, `nextMentions` extracts all successors from the final five lines, then launches their child branches concurrently. All three constraints are required: **serialize execution for the same member** (if two branches name the same member, the later one queues; otherwise two simultaneous streaming messages break the transcript's "latest message" and folding rules), the concurrency limit `MAX_PARALLEL`, and the total hop limit `MAX_TOTAL_HOPS` (`MAX_HOPS` only limits the depth of a single path, not the total after branching). These live in `HopScheduler` and `GroupChainGuard` in `group-chain.ts`. **Fork a separate guard for each branch**: it checks whether "this path is looping"; sharing one object between sibling branches produces false cycles. Parallel siblings **cannot see each other's output from the current turn** (the transcript includes only non-streaming messages). This is inherent to parallel execution and is explicitly explained to the model in the collaboration protocol's "You are not running alone" section, rather than left for it to discover by accident. The orchestration **explicitly passes down** each hop's assignment (`assignment` in `buildGroupTranscript`); do not infer it from "the last entry in the history", which in parallel execution may not be the member handing work to it.

**The deliverables checklist is derived, not a new table** (`shared/group-deliverables.ts`): each member has a `deliverable` filled in at group creation, and messages carry `author`; combining the two yields the checklist. Use **the document structure itself** as the criterion: a deliverable is that member's **latest complete message whose first line is a level-one heading**. The collaboration protocol requires professional documents to begin with `#` and convergence hops with `##`, so convergence messages do not occupy deliverable slots, and revised versions automatically replace older ones, without adding fields or tables (content exists only once in messages; saving another copy would immediately create a second source of truth). This single derivation feeds three places: each hop's system prompt's "Deliverables checklist for this turn (N/M)" (**the checklist defines "done"**; remaining hops merely apply pressure), the renderer's deliverables panel, and `group:export`. Export includes only deliverables, strips trailing handoff lines, and converts structured mentions to `@name`. **Never have the model write a "summary document"** (it would copy everything again, doubling the output and quietly changing the original authors' judgments).

**Parallel branches must converge**: when a hop branches into ≥2 paths, automatically return control to **the member who assigned the work** for another hop after all child branches settle (the section after `settleBranches` in `runBranch`). Without convergence, parallelism only buys speed: the user receives N documents unaware of one another and must mentally merge them and resolve conflicts. The convergence hop's collaboration protocol strictly limits it to **comparison + filling gaps + deciding the next destination**, explicitly stating "do not rewrite their documents" (when a model sees three documents, the easiest approach is to copy them into a fourth, doubling output and quietly changing the original authors' judgments). Converge only after a real fork (a single branch is a linear handoff, and that member already has all the context). **Do not automatically converge when the user directly mentions multiple members**: the user assigned the work at this level and is also responsible for closing it out (if a lead role is introduced later, this is where it belongs). If the guard blocks a convergence hop, **do not report a stop**: the documents have already been persisted; skipping one merge is degradation, not failure.

**Convergence depends on visible budgets, not abrupt cutoffs**: `GroupChainGuard.budget()` injects "current hop / remaining hops" into each hop's system prompt, explicitly requiring closure when ≤2 hops remain (the guard's gate is only a fallback; being stopped leaves the user with a pile of unfinished work). The collaboration protocol's handoff threshold is **binary**: the only valid reason to hand off is "there is a specific task you cannot do". Review outputs must provide "Verdict: pass/fail + list of blocking issues"; with 0 blocking issues, they must @-mention the user. "It could still be improved" is not a reason to hand off, and each deliverable may undergo at most one round of rework. When changing this, remember: **open-ended suggestions are infinite; blocking issues are finite**. Rules must target the latter.

Event semantics change accordingly: `chain-stopped` and `error` are both **branch-level**; only `chain-done` means "all branches have finished", and the renderer clears running state only on that event (`speakingByMessage` in `stores/collab.ts` is also keyed by messageId; a single value would mix parallel chunks into other members' messages). A stop is still not the end: `chain-stopped` carries `nextMemberId`, and the renderer offers a one-click "Let them continue the handoff" action (send a new message to start a new chain, resetting the guard with it; the human is the loop's checkpoint).

The transcript has a context budget (`group-transcript.ts`, calculated from the member model's contextWindow): when exceeded, fold old messages into heading-outline stubs (with message IDs). **Never fold user messages, each member's latest message, or the previous hop**; restate the previous hop's handoff instructions at the end. After a hop finishes, asynchronously generate a rolling "story so far" digest (`group-digest.ts`, stored in `group_digests` as a derived cache, excluded from synchronization; prefer the global auxiliary model assistantModel, falling back to the finishing member's model only when unconfigured; metered as scene='group_digest'). During folding, the digest block replaces the stubs it covers. Digest generation failures silently fall back to mechanical folding and must never block the handoff chain. When an agent needs folded original text, use list_group_messages / read_group_message in `group-tools.ts` to read it back by line range (read-only and idempotent, sharing the tool budget; results are not persisted).

### Preview pipeline (src/main/preview/)

The custom `preview://` protocol compiles vue3/react SFC/TSX into ES modules in the **main process** and serves them directly (`compile.ts`, @vue/compiler-sfc / oxc-transform). The iframe contains only an import map and mounting code, with no compiler. Key points:

- For relative imports, the browser itself sends requests back to the protocol layer; **no dependency crawling is needed**.
- Extensionless imports (`import '../useUsers'` → `useUsers.ts`) are completed by `resolve.ts` using bundler rules. Changes to resolution rules must include tests (`resolve.test.ts`).
- Bare imports rely on the import map (`VENDOR_IMPORTS` in `bootstrap.ts`); vendor files are prepared by `scripts/prepare-preview-vendor.mjs`. Project-selected component libraries (`project.libs`) use a CDN import map; **consult the checklist in `docs/preview-libs.md` when adding a library**.
- All three stacks share Tailwind v4 + a per-project generated `theme.css` (driven by StyleBrief as the first choice; on the first turn of an empty project, after the user skips, a non-persisted independent-dimension fallback may be used; injected at preview runtime by exact root-path matching).
- Compilation failures return 200 + `throw` (not 500): the error text must reach the iframe's catch handler and flow back to the model.
- **Preview annotations** (the user clicks elements and writes notes for AI): the iframe has a different origin, so the parent window cannot read its DOM. Picking, highlighting, and numbered badges therefore all live in `annotate-runtime.ts` (inlined by `COMMON_HEAD`, shared by all three stacks); both sides communicate only through postMessage (`__previewCmd` downward / `__preview` upward). vue3 injects `data-antd-src="file:line:column"` into ordinary elements at compile time (`sourceLocTransform` in `compile.ts`; inline-template loc uses absolute file lines, while separately compiled templates need their block offset added; `compile.test.ts` pins this convention and the hardcoded compiler-core enum values). For html / react, element signatures let the model use `search_files`. Annotations **do not enter IPC, the database, or the system prompt**: they express the intent of this user message and are appended to the message body by `attach.ts::composeMarks`, then cleared after sending (the same semantics as attached files); markers are invalidated by artifactId.

### Key renderer conventions (src/renderer/)

- `stores/chat.ts`: streaming state is **isolated by conversation** (`streams: Record<conversationId, StreamState>`), each stream has a buffer (parts/activities/reasoning), and message objects and buffers **share references**. When switching away, deltas go into the buffer; switching back resumes from it without losing a chunk. Read the StreamState comments before changing this.
- **Canvas ownership is determined solely by projectId, not conversationId**: `artifact.applyStreamEvent(event, ownerProjectId)` checks for itself whether the stream belongs to the current project; keep the check on the data owner's side (so a caller's missing check cannot cause cross-project mixing). Historical lesson: the gate once compared `conversationId`, but the canvas project identity changed **synchronously** on the first line of `loadForProject`, while conversation identity changed only after an IPC round trip in `ensureDesign`. That window was enough for the previous project's still-running stream to insert files into the new project's tree, leaving pending entries that would never receive `file-end`. Likewise, `afterNewVersion` must **never select an artifactId absent from this project's version list**; every await in `loadForProject` / `select` must be followed by a guard; and `files/currentId/selectedPath` must be **cleared synchronously** when switching projects (clearing only pending entries leaves the previous project's whole tree visible for tens of milliseconds longer). Regression coverage for these rules lives in `stores/artifact.test.ts`.
- Selection semantics: `null` = never selected = **load nothing** (equivalent to an empty array); skill/MCP selections are stored by **name** (there is no id).
- Message rendering is **sequentially interleaved**: response text and tool calls alternate in occurrence order (`components/message-segments.ts`), rather than tools being piled at the bottom of the bubble. Order is reconstructed using `ToolActivity.afterChars` (the number of response-body characters already written at tool-start). Tool activities are not persisted, so there is no other way to know "what was said before the tool was called". Entries missing this field (old messages reloaded from the database) always go at the end, falling back to the old behavior. Parallel calls at the same position are grouped and passed to `ToolActivityList` for collapsing.
- Monaco: reuse `@renderer/monaco/{setup,highlighter}`; the model pool in `monaco/vfs.ts` is a singleton dedicated to design artifacts. Other features needing an editor must create their own models and manage disposal themselves (see `pages/skill-editor/`).
- Always obtain `message/modal` through `App.useApp()` for dialogs/messages; do not use static imports (they cannot access the ConfigProvider context).

## antdv-next component library pitfalls (verified in practice)

- Tag slots swallow child elements; place text directly in the slot.
- There is no List component; use the `titleRender` slot for Tree and `size` for Drawer dimensions.
- Prefer `a-segmented` for switching UI (a project aesthetic preference; do not use a-tabs).

## Other mandatory conventions

- Overlay content must have a maximum height and scroll internally (`max-height` + `overflow-y: auto` + `overscroll-behavior: contain`); do not let it force a scrollbar onto the page.
- The stop button during streaming is "Pause", not a red danger button.
- Escape ``` in user content inlined into the system prompt to prevent breaking out of code fences; pass model-generated/remote URLs through `web/ssrf.ts` before accessing them.
- Write commit messages and documentation in English.
