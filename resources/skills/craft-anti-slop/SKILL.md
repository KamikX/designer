# 避免无意落入模板

**先读 StyleBrief，它高于本文。** 当项目已有明确的颜色、渐变、字体、几何、排版或构图
方向时，按该方向实现；不能因为某个视觉特征看起来常见就要求重做。

## 无明确 StyleBrief 时的 fallback 检查

以下是发现“模型随手套模板”时的提问清单，不是违规清单。命中后先检查它是否服务内容、
品牌与交互；没有明确意图时，再从中选择一项做得更具体。

- 常见靛蓝、双色渐变、emoji 图标、圆角卡片配彩色竖条，可能只是默认组件的拼接；也可能
  正是项目已确认的品牌语言。
- 完全对称的区块、惯性地重复“首屏 → 功能 → 价格 → FAQ → 行动号召”、波浪或斑点背景，
  可提示重新核对内容节奏与信息层级，而非强制换成某一种布局。
- 标题、正文和数据应消费已确认的 theme.css 字体语义；全 sans、衬线或混合体系都可以，
  只要符合 StyleBrief。
- 外部占位图服务、零散字面色值和整套旧种子指纹值得检查：它们可能分别造成资源不可靠、
  token 漂移或没有生成项目主题。

## 不随审美改变的底线

- **内容真实性。** 不编造数字、来源、案例或能力；没有真值时使用诚实的占位与说明。
- **功能完整性。** 可操作控件有可理解的状态和反馈；加载、空、错误及危险操作不被省略。
- **可访问性。** 文字、控件和焦点有足够对比度，状态不只靠颜色，键盘操作可用。

## 诚实的占位

拿不到真实数值时,写 `—` 或一个带标注的灰块,**不要编一个**。
一个诚实的占位胜过一个假数据 —— 后者会让整个产出立刻失去可信度。

## 让页面有具体性

从 StyleBrief、真实内容与用户任务中选择一两个具体决定：产品特有的措辞、可验证的数据、
记得住的交互反馈，或能解释业务的布局比例。它们应强化项目方向，而不是满足固定的“独特”
配额。

## 交付前的两秒直觉检查

如果页面脱离产品名称后仍像任何同类产品，回看 StyleBrief 与内容事实，补足一个真正服务用户
任务的细节。不要以删颜色、换字体或打破对称作为机械答案。
